# Relatório final

## Tabela de diagnóstico - Etapa 1:
| Categoria | Anomalia encontrada (e onde) | Por que é um problema |
| :--- | :--- | :--- |
| 1. Adequação e lógica | 1. Mistura de regras de negócio com I/O. As funções add e rem tem instruções de saída (cout << "Remarcado", etc.) embutidas. <br> 2. Falta de verificação de sobreposição parcial. Na função add e rem, o código checa apenas se o horário (h) é exatamente igual ao agendado. | 1. Funções com dupla responsabilidade devem ser separadas em outras funções de responsabilidade única, impedindo readequação ou aproveitamento de interfaces gráficas. <br> 2. Se um agendamento dura 60 minutos e começa às 14h, o sistema permite marcar outro no meio da consulta (ex: 14:30), pois o cálculo ignora a duração (dur) na colisão de horários |
| 2. Manutenibilidade | 1. Ao decorrer de todo o código são encontradas variáveis mal nomeadas, utilizando, na maioria das vezes, uma única letra. Exemplo: Todas as variáveis do struct e até o próprio struct "A".<br> 2. A função add tem quatro comandos if aninhados sucessivamente e um for. <br> 3. Comentários explicando códigos confusos como: // adiciona na lista na função add e // remarca o atendimento em rem.| 1. Variáveis com nomes ruins e sem padrão carecem de significado, dificultando o entendimento de quem está lendo o código e prejudicando totalmente a manutenibilidade, já que agora, o tempo voltado a entender a lógica do código, foi tomado por entender o que cada letra significa. <br> 2. A função é difícil de ler, não retorna rápido e tenta fazer muitas validações acumuladas. <br> 3. O nome da função já deve deixar claro o que ela faz. Comentários devem explicar os "porquês" das decisões técnicas e de negócio, e não narrar o que o código está fazendo.|
| 3. Organização e estética | 1. A lógica de varrer o vetor procurando um conflito de horário é idêntica dentro de add e repetida dentro de rem. <br> 2. Código morto. Há uma função // void desmarcar(...) que foi totalmente comentada e abandonada no arquivo | 1. Se a regra de verificação de horários mudar, o desenvolvedor terá que alterar esse trecho manualmente em cada aparição sua, o que facilita introdução de novos bugs. <br> 2. Polui o código e cria confusão visual. Trechos inúteis ou deprecados devem ser deletados ou implementados de uma vez. |
| 4. Programação defensiva e segurança | 1. Captura de erros genéricos e sem tratamento adequado na função add. Com catch(...). <br> 2. Falta de validação de entradas. Não há verificação para garantir que o nome do paciente (p), o médico (pr) ou a data (d) não sejam strings vazias ("").  | 1. Como o erro não é capturado de forma específica, ele também não é tratado, então qualquer erro que seja capturado é abafado de forma silenciosa, podendo causar problemas maiores e inesperados. <br> 2. Parâmetros externos devem ser validados logo na entrada. Atualmente, o sistema permite marcar consultas com campos inexistentes |
| 5. Desempenho e recursos | 1. Busca sem interrupção. Nos laços for dentro de add e rem, o loop continua percorrendo o array inteiro mesmo após já ter encontrado uma colisão de horário (ok = false).| 1. Gera iterações desnecessárias. Faltou um comando break ou um return imediato após constatar que o horário já está ocupado.|
